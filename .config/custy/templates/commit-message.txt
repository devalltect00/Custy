feat(core): support project-aware workflows across repository layouts

Add runtime project discovery, ecosystem-aware version metadata
synchronization, safer initialization, resilient template loading, correct
message-backup routing, and a protected CLI error boundary. This development
checkpoint removes the former assumption that every target repository owns an
`app/` directory or Python version module while improving release-workflow
reliability ahead of Custy v2.1.0.

### 🧭 Project Layout Detection

- Detect Python, Node.js, PHP, mixed, and generic repositories from conventional root metadata.
- Resolve source directories at command runtime instead of validating a global `app/` path during import.
- Prefer `app/` then `src/` for Python projects, and `src/` then `app/` for Node.js and generic projects.
- Safely fall back to the project root when no conventional source directory exists.
- Keep explicit `project_source` overrides strict and provide actionable configuration errors for missing or invalid paths.
- Treat a missing Custy configuration as an expected uninitialized-project state instead of emitting startup noise.

### 🔢 Cross-Ecosystem Version Metadata

- Add automatic discovery for existing Python `__version__.py`, static `[project].version` in `pyproject.toml`, and string `version` values in `package.json`.
- Synchronize supported Python and Node.js metadata in mixed repositories.
- Update root Node.js lockfile metadata when applicable.
- Normalize tag values before writing project metadata so a leading `v` remains a Git tag prefix rather than part of the stored package version.
- Preserve strict validation for explicitly configured version targets.
- Allow repositories without supported version metadata to use Git-tag-only versioning instead of failing validation.

### 🏗️ Project-Aware Initialization

- Generate `project_source = "auto"` and `version_file = "auto"` in newly initialized Custy configuration.
- Preserve existing Python and Node.js version metadata during initialization.
- Create a Python `__version__.py` only for a detected Python project that has no supported version metadata.
- Avoid creating artificial Python files in Node.js, Docusaurus, PHP, documentation-only, or generic repositories.
- Retain recursive copying for nested commit and tag message examples.

### 📝 Changelog and Message Template Reliability

- Load the packaged changelog template when an uninitialized project does not yet have `.config/custy/templates/changelog/changelog.j2`.
- Preserve project-owned changelog templates as the highest-priority override after initialization.
- Raise an actionable configuration error when an explicitly configured custom template cannot be found.
- Honor the configured tag-message backup directory instead of falling back to an unrelated default location.
- Add focused coverage for packaged fallback loading, project override precedence, missing custom templates, and tag-message backup routing.

### 🧰 Developer Workflow and Pre-Commit

- Expand Make helpers for installing, updating, validating, cleaning, refreshing, and running pre-commit hooks.
- Invoke pre-commit through its correct Python module name, `python -m pre_commit`, for reliable virtual-environment execution.
- Make `pre-commit-refresh` update revisions, rebuild hook environments, install hooks, and validate all repository files.
- Refresh Ruff from `v0.12.0` to `v0.16.4`, pre-commit-hooks from `v4.6.0` to `v6.0.0`, and Black from `25.1.0` to `26.5.1` for the Python 3.14 development toolchain.
- Use Ruff for linting and automatic lint fixes while keeping Black as the single Python formatter.
- Protect inactive `old`, `example_before`, copied, deprecated, development, and temporary Python references from direct and pre-commit-driven formatting.

### 🧯 CLI Reliability and Error Handling

- Route console and module execution through a centralized protected entry point.
- Render known configuration and validation failures as concise, actionable Custy errors without duplicate tracebacks.
- Summarize unexpected failures in normal mode and preserve full tracebacks when `--debug` is requested.
- Propagate initialization failures to the shared error boundary instead of printing the same failure twice.
- Make a no-subcommand invocation display root help and exit successfully for interactive and container discovery.
- Limit routine pipeline traceback logging to debug mode.

### 🐳 Docker and Packaging

- Point the installed `custy` console script at the protected application entry point.
- Verify the production image against a mounted Docusaurus repository with no `app/` directory.
- Confirm that no-command and explicit-help container invocations exit successfully.
- Confirm that `custy --dry-run init --mode all` previews initialization without changing mounted project files.
- Keep TOMLKit available in the production dependency set for project metadata updates.

### ✅ Tests and Quality

- Add focused detector coverage for Python, Node.js, mixed, PHP, and generic layouts.
- Add cross-project version-update tests for Python modules, `pyproject.toml`, `package.json`, lockfiles, mixed repositories, and tag-only repositories.
- Add protected-entry-point, structured-error, no-subcommand, and cross-project startup regression tests.
- Update initialization, resolver, validation, and workflow tests for optional automatic version targets.
- Align Ruff and Black configuration with the active source tree while excluding protected historical and temporary reference files.
- Apply import, formatting, typing, and lint cleanup across active application and test code.
- Validate the refreshed pre-commit configuration before release.
- Validate the complete suite with 1,179 passing tests and 82% overall coverage.
- Confirm `ruff check .`, `black --check .`, and `git diff --check` complete successfully.
- Validate the rebuilt `custy-prod:latest` image from the Devalltect documentation repository.

### 📚 Documentation

- Document automatic project-source and version-target detection in the canonical Custy guide.
- Explain initialization and versioning behavior for Python, Node.js, mixed, and generic repositories.
- Add Docker guidance for repositories without an `app/` directory.
- Add migration and troubleshooting guidance for older explicit path configuration.
- Keep English and Indonesian Custy documentation behaviorally aligned for v2.1.0.

### ⚠️ Compatibility Notes

- Existing explicit paths such as `project_source = "app"` and `version_file = "app/__version__.py"` remain strict by design.
- Projects that want automatic discovery must change those values to `"auto"` or run initialization in a reviewed replacement workflow.
- Existing editable installations should be reinstalled after updating source so the generated `custy` console script uses the protected entry point.
- The experimental status of `custy workflow` is unchanged.
