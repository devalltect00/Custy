Yes, exactly.

I actually think this is the most future-proof design for Custy.

The key idea is:

> **Custy should generate a clean changelog by default, but everything that is "project-specific" should be configurable.**

Contributor information is definitely project-specific.

---

# My recommendation

By default

```toml
[tool.custy.changelog.contributors]

enabled = false
```

Most personal projects don't need it.

Many small repositories have only one developer.

Showing

```
Contributors

• Rizky Fernandes
```

for every release doesn't add much value.

---

For larger projects

```toml
[tool.custy.changelog.contributors]

enabled = true
mode = "release"
```

or

```toml
[tool.custy.changelog.contributors]

enabled = true
mode = "section"
```

or

```toml
[tool.custy.changelog.contributors]

enabled = true
mode = "entry"
```

depending on the team's preference.

---

# I would even make it richer

Instead of only

```toml
enabled = true
```

I'd expose options like

```toml
[tool.custy.changelog.contributors]

enabled = true

mode = "release"

show_name = true

show_email = false

show_profile = true

show_commit_count = true

sort = "commit_count"
```

Then Custy can automatically generate

```
Contributors

• Rizky Fernandes (18 commits)
• Alice (7 commits)
• Bob (3 commits)
```

or

```
Contributors

• Rizky Fernandes
  https://github.com/devalltect00

• Alice
  https://github.com/alice
```

depending on the configuration.

# Where should Contributors appear?

This is the part I have the strongest opinion about.

I **would not** put it in the global header.

For example, I would **not** do this:

```md
# 🧾 Changelog

...

Contributors

• Alice
• Bob
• Charlie
```

because those contributors may only have worked on one release.

The global header should describe the document, not the people.

---

## I also would not put it in the footer

For example:

```md
## 1.10.6

...

Metadata

...

Contributors

...
```

The footer should be reserved for technical metadata like:

* Tags
* Release type
* Scope
* Build information

Contributors are much more important than metadata.

---

# Where should the information come from?

I actually wouldn't ask users to manually maintain contributor names in `config.toml`.

Instead, I'd use this priority:

1. **Git history (default)** – Read commit authors automatically for the commits included in that release.
2. **GitHub/GitLab username mapping (optional)** – A configuration section can map Git identities to profile URLs or display names when the automatic information isn't sufficient.
3. **Manual overrides (optional)** – Allow the user to rename or hide contributors if needed.

For example:

```toml
[tool.custy.changelog.contributors]

enabled = true
mode = "release"
show_profile = true

[tool.custy.changelog.contributors.aliases]

"rizkyslenovo29@gmail.com" = { name = "Rizky Fernandes", profile = "https://github.com/devalltect00" }

"alice@example.com" = { name = "Alice", profile = "https://github.com/alice" }
```

This avoids duplicating information that's already in Git while still giving users complete control over how contributors are presented.

## My final recommendation

If I were locking Custy's changelog specification today, I would make contributors an **optional release-level feature**:

* Disabled by default.
* Automatically collected from Git when enabled.
* Configurable through `config.toml` (display names, links, sorting, commit counts, etc.).
* Displayed immediately after the release status (or within a compact "Release Information" block) and before the summary.

That keeps the changelog focused on the release itself while making contributor recognition available for open-source and team projects where it adds real value. I think it fits Custy's philosophy of being structured, flexible, and highly configurable.
