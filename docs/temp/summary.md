I think we've reached the point where we should **lock the CHANGELOG specification**. Once we agree on this, we should treat it like a public API: every parser, model, processor, and Jinja template should target this structure. Future features (GitHub Releases, GitLab Releases, HTML documentation, JSON export, RSS feeds) can all build on the same semantic model.

This is the specification I would approve for Custy.

---

# If subsection has only one generic category

Input commit

```md
### 🐛 Bug Fixes

#### main

- Fixed parser.
- Fixed workflow.
```

Output

```md
### 🐛 Bug Fixes

- Fixed parser.
- Fixed workflow.
```

Because

```
main
```

adds no information.

# Configuration

Everything becomes configurable.

```toml
[tool.custy.changelog.render]

show_compare_link = true
show_status = true
show_summary = true
show_contributors = false
show_statistics = false
show_metadata = true
show_tags = true
collapse_generic_subsections = true
show_empty_sections = false
```

Then

```toml
[tool.custy.changelog.contributors]

enabled = false

mode = "release"

show_profile = true

show_commit_count = true

sort = "commit_count"
```

# The semantic model

I think this is the model Custy should target.

```
Changelog
│
├── Header
│
├── Releases
│      │
│      ├── Version
│      ├── Date
│      ├── Compare Link
│      ├── Status
│      ├── Contributors (optional)
│      ├── Statistics (optional)
│      ├── Summary
│      ├── Sections
│      │      │
│      │      ├── Features
│      │      │      ├── Workflow
│      │      │      └── Parser
│      │      │
│      │      ├── Bug Fixes
│      │      ├── Improvements
│      │      ├── Documentation
│      │      ├── Templates
│      │      └── ...
│      │
│      └── Metadata (optional)
│             ├── Release Type
│             ├── Scope
│             ├── Classification
│             └── Tags
│
└── Footer (optional)
```

## One improvement I'd make before we implement it

There's one thing I'd tweak from the draft above.

Instead of having separate standalone labels like:

```text
Status

Stable Release

Contributors

• Rizky Fernandes

Summary

...
```

I'd group them into a **Release Information** block. It keeps every release visually consistent and makes scanning easier.

```md
## 1.10.6 (2025-08-06)

🔗 Compare

https://github.com/devalltect00/Custy/compare/1.10.5...1.10.6

Release Information

• Status: Stable Release

• Contributors:
  - Rizky Fernandes
  - Alice

• Promoted From:
  - 1.10.6rc4
  - 1.10.6rc3
  - 1.10.6rc2
  - 1.10.6rc1
  - 1.10.6b1

Summary

Final release of Custy 1.10.6 focused on workflow safety, merge validation, template quality, and user experience.

### ✨ Features
...
```

I think this is cleaner because all of the **release metadata** lives in one place before the reader gets to the actual changes.

---

**I would be comfortable locking this as Custy CHANGELOG Specification v1.0.**

Once you approve it, we should **not change the output format anymore** unless it's a backward-compatible improvement. From that point on, we'll adjust the parser, processing pipeline, models, and Jinja template so they all produce this specification consistently. This gives Custy a stable, professional changelog format that is structured, extensible, and much easier to read than a raw commit log.
