I actually think this is the point where we should **freeze the CHANGELOG specification** before writing more code.

From everything you've explained, I don't think Custy should generate a "git log". I think it should generate a **Release Document**.

The commit message is written for developers.
The CHANGELOG is written for users (including future you).

Those are different audiences.

---

# Custy CHANGELOG v2 (My Proposed Specification)

```markdown
# 🧾 Changelog

All notable changes to Custy are documented in this file.

This changelog is generated by Custy from structured commit messages.
Versions are listed in reverse chronological order.
```

#stable

#docs

I'd render

Documentation

No raw hashtags.

Because

```

```

means nothing to a user.

But

```
Workflow
```

does.

# The parser

I think your parser should recognize this structure.

```
Header

↓

Summary

↓

Metadata

↓

Sections

↓

Footer
```

instead of

```
Header

↓

Body

↓

Split into lines
```

That is where almost every problem you're currently seeing originates.

# The internal model

I would actually redesign the release model into something like this:

```text
Release
│
├── version
├── date
├── compare_url
├── status
├── summary
├── promoted_from
├── sections
│   ├── Features
│   ├── Fixes
│   ├── Improvements
│   ├── Documentation
│   ├── Templates
│   └── ...
├── metadata
│   ├── release_type
│   ├── scope
│   ├── classifications
│   └── tags
└── custom_message
```

Notice there is **no raw body anymore**.

Everything has meaning.

## One final suggestion

If I were designing Custy as an open-source project, I would make the CHANGELOG look less like a commit log and more like a **mini release page**.

Every release would answer four questions in the same order:

1. **What is this release?** (version, date, compare link, status)
2. **Why does it exist?** (summary)
3. **What changed?** (features, fixes, docs, refactoring, etc.)
4. **How should I classify it?** (metadata such as release type, scope, and tags)

That makes the file readable whether someone is scanning six releases or hundreds. It also maps naturally onto the structured models you've already started building, so the renderer becomes much simpler and future outputs (GitHub Releases, GitLab Releases, JSON, website release pages) can all be generated from the same data instead of parsing free-form text again.

I think this direction fits Custy much better than trying to imitate a traditional changelog while still preserving the richer information that your structured commit template provides.
